A parcel company's support desk, run by a team of AI agents

Customers of SwiftParcel, a fictional delivery company, ask about refunds, missing parcels and insurance for broken items. Each message is passed between specialist agents. One understands it, one looks up the order, one checks the company rules, one takes action, and one writes the reply. Money only moves when the rules allow it, and anything over the approval limit waits for a person.

        Support lead queue

        The agents never pay a large refund or claim on their own. When one is above the approval limit, the execution agent opens a ticket and parks it here. A person reviews it and decides. Only after an approval does the system pay, and the payment records who approved it.

        How it works

        Support teams at delivery companies spend most of their day on three questions: where is my refund, where is my parcel, and can I claim for a damaged item. Each one needs several systems and a policy check. This project automates them safely, and proves it with automated tests.

        The route every message takes

        1. Safety checkBlocks attempts to trick the system, like "ignore your instructions", before any AI reads them.Code
        2. Intent agentWorks out what the customer wants and which order they mean, using earlier messages when needed.AI + rules
        3. RouterSends the request down the refund, tracking, insurance or general-help route.Code
        4. Lookup agentFetches order, delivery, return and refund records. It can read, never change anything, and only for this customer.AI + checks
        5. Policy agentApplies the company rules and gives a yes or no with the rule number. Plain code, so the same facts always get the same answer.Code
        6. Execution agentThe only agent allowed to pay, file a claim or open a ticket. Above the limit, it asks a person instead.Code
        7. Response agentWrites the reply with references to the records and rules it used, then a final check stops anything false or off-limits.AI + checks

        Why the money decisions aren't made by AI

        Language models are excellent at understanding messy messages and writing clear replies, so that's where this system uses Claude. Deciding whether a refund is allowed is different: it has to be exact, repeatable and explainable to an auditor. So the rules are ordinary code, and the AI has no way to call the payment tools. Even if someone tricked the AI, it couldn't move money.

        What it remembers

        Each conversation keeps a short history plus a few working facts, like which order is being discussed. That's why "It arrived smashed, can I claim?" works without an order number, and why asking "any update?" after an approval gets the right answer.

        Every request leaves a trail

        The tracking timeline you watched in the demo is the real operational record. Each request gets a trace with every step, every record lookup, every AI call with its token cost, and the final decision. Every action is also written to an audit log with the reason it was taken. Those logs drive the alerts an on-call engineer would get at 2 AM, such as a rising error rate or an unusual number of refunds.

        What it's built with

        • Claude Haiku 5.5 from Anthropic, chosen because these are short understanding and writing tasks where a larger model adds cost, not accuracy
        • Python, with the Anthropic SDK and no agent framework, so every permission is explicit
        • FastAPI and live streaming for this website
        • Docker for packaging, and automated tests on every change

        Test results

        The system is checked against a fixed set of customer requests with known correct outcomes, including deliberate attacks and mistakes. A change is only accepted if these tests still pass.
